# Урок 8, блок B: локальний Backend API

## Урок 9: AI-аналіз через Google Gemini

`POST /api/ai/analyze-transactions` без тіла запиту, з чинним
`Authorization: Bearer <ADMIN_PASSWORD>`. Навіть JSON `{}` відхиляється (422).
Спочатку виконуються наявні локальні перевірки та `require_admin`, потім
перевірка конфігурації, лімітів і читання фінансів. Власник визначається тільки
`API_ALLOWED_USER_ID`; query-параметри не змінюють власника, період або модель.

Аналіз охоплює сьогодні та попередні 29 календарних днів у `Europe/Kyiv`,
за полем `transactions.date`, включно з обома межами. `created_at`, пагінація
та фільтр таблиці на нього не впливають. Дати повертаються в `period_start`
і `period_end`. Це підсумок зареєстрованих операцій, а не банківський залишок.

Приклад відповіді з вигаданими даними:

```json
{
  "period_start": "2026-10-25",
  "period_end": "2026-11-23",
  "currency": "UAH",
  "transaction_count": 3,
  "total_income": "1000.00",
  "total_expense": "250.00",
  "balance": "750.00",
  "summary": "За період записані доходи перевищують витрати.",
  "top_expense_categories": [
    {"category": "Продукти", "amount": "250.00", "share_percent": "100.00"}
  ],
  "risks": ["Неповний облік може обмежувати достовірність висновків."],
  "advice": ["Регулярно перевіряйте повноту записаних операцій."]
}
```

Backend одним SQL statement читає узгоджений знімок агрегатів дозволеного
власника. PostgreSQL рахує NUMERIC SUM/COUNT, Python використовує Decimal
для балансу, залишку інших витрат і часток. П'ять найбільших категорій
сортуються за сумою спадно, при однаковій сумі — за назвою. Частка від усіх
витрат округлюється до двох знаків ROUND_HALF_UP; окремо округлені частки
можуть у сумі трохи відрізнятися від 100%. Суми повертаються рядками.
Сесія БД закривається до виклику Gemini. Записів і міграцій немає.

До Gemini передаються тільки період, валюта, кількість доходів/витрат,
їхні підсумки, баланс, топ категорій під тимчасовими позначеннями category_N
та сума решти витрат. Назви категорій, описи, окремі транзакції, user_id,
Telegram-ID і службові поля не надсилаються. Справжні назви категорій,
суми й частки у відповіді формує backend. Модель створює лише три текстові
поля: summary, risks, advice. Системна інструкція вимагає українську мову,
обережні висновки, відсутність вигаданих фактів і числових тверджень у прозі.
За порожньої історії повертається 200 із нульовими сумами, порожніми списками
та поясненням без виклику Gemini (за умови, що AI налаштовано).

Використовується офіційний `google-genai==1.75.0`, асинхронний клієнт у
lifespan із закриттям обох HTTP-клієнтів на завершенні. `tzdata` забезпечує
Europe/Kyiv також у Windows і мінімальних контейнерах. Ключ читається лише
з `GEMINI_API_KEY` і явно передається SDK; GOOGLE_API_KEY та старий AI_API_KEY
не вмикають інтеграцію. Клієнт використовує Gemini Developer API, без Vertex AI.

Конфігурація backend, яку оператор задає через середовище або Uvicorn
`--env-file .env` (імпорт модулів не завантажує env-файлів):

| Змінна | За замовчуванням | Обмеження |
| --- | --- | --- |
| `GEMINI_API_KEY` | відсутній | секрет лише backend; відсутній/порожній вимикає AI |
| `GEMINI_MODEL` | `gemini-3.8-flash` | ідентифікатор моделі Gemini; доступність залежить від проєкту |
| `GEMINI_TIMEOUT_SECONDS` | `30` | ціле 1–120, SDK timeout і загальний дедлайн генерації |
| `GEMINI_DAILY_LIMIT` | `20` | ціле 1–1000, кількість дозволених спроб за київську добу |

Модель за замовчуванням позначена Stable в офіційному
[каталозі моделей Google](https://ai.google.dev/gemini-api/docs/models).
Реальний доступ до моделі та білінг у межах автоматизованих тестів не перевіряються.
Некоректна конфігурація або помилка створення клієнта вимикає AI через 503,
не блокуючи попередні API. Не передавати ключ у VITE_*, frontend або Git.

Лімітатор допускає один аналіз одночасно, без черги, і мінімум 60 секунд
між початками спроб. Добовий ліміт скидається опівночі Europe/Kyiv; cooldown
при цьому зберігається. Лічаться всі допущені спроби, включно з порожніми
даними, помилками БД/провайдера і таймаутами; відмови авторизації, некоректне
тіло та відсутня конфігурація його не витрачають. Ліміт не повертається після
помилок, оскільки провайдер міг уже виконати генерацію.

У SDK явно задано `attempts=1`: автоматичних повторів немає. Генерація має
одного кандидата, максимум 2048 вихідних токенів, без tools і автоматичного
виклику функцій. Thinking level — LOW для меншої затримки та витрат; модель
із GEMINI_MODEL повинна підтримувати цей режим і структуровані відповіді.
JSON-схема задається з Pydantic; відповідь повторно
валідується. Відхиляються blocked/partial/non-STOP відповіді, tool calls,
невалідний JSON, зайві поля, порожній текст і перевищення обмежень.
Summary: 1–1200 символів; risks/advice: до 5 пунктів по 1–500 символів;
top_expense_categories: до 5. Читання фінансового знімка має дедлайн 10 секунд.

| HTTP | Значення |
| --- | --- |
| 401 | відсутній/невірний адміністративний пароль |
| 403 | локальний захист Host/Origin/Fetch Metadata/loopback |
| 422 | передано непорожнє тіло |
| 429 | одночасний запит, cooldown, добовий ліміт або квота Google; є Retry-After |
| 502 | невалідна, заблокована або обірвана генерація |
| 503 | вимкнений адміністративний доступ, AI не налаштовано, БД/провайдер недоступні |
| 504 | таймаут Gemini |

Помилки credentials/model провайдера маскуються як 503: вони не означають
невірний пароль адміністратора. Логи застосунку містять лише коди подій,
без prompt, заголовків, тексту SDK-помилок, ключів чи фінансових даних.
Усі HTTP-відповіді зберігають no-store та nosniff. Не вмикати діагностичне
логування мережевого транспорту із заголовками/тілами та не експортувати HAR.

Обмеження: ліміти зберігаються лише в пам'яті одного процесу й скидаються
після restart. Використовувати один Uvicorn worker; для кількох процесів або
надійного бюджетного ліміту потрібне спільне сховище. Це обмежує кількість
спроб, але не гарантує суму рахунку Google. Скасування/таймаут не доводять,
що провайдер не врахував запит. JSON-валідація гарантує форму, а не істинність
або мову текстових висновків; числові факти перевірені backend і показані окремо.

Ізольовані перевірки без Gemini, .env і Neon:

```powershell
.\.venv\Scripts\python.exe -B -m pytest tests/test_ai_analysis.py tests/test_gemini_client.py tests/test_transactions_api.py tests/test_transaction_post.py tests/test_transaction_delete.py -p no:cacheprovider -q
```

HTTP-тести використовують in-memory SQLite та mock Gemini. Транспортні тести
працюють зі справжнім зафіксованим SDK через httpx.MockTransport, включно
з перевіркою одного HTTP-запиту при 429/5xx і таймаутах. Справжні ключі
прибираються із середовища тестів; синтетичні використовуються лише з mock.
SQLite не доводить NUMERIC-семантику PostgreSQL: точна Decimal-арифметика
додатково перевіряється на великих контрольованих агрегатах. PostgreSQL-набори
залишаються доступними лише через наявний opt-in disposable local_engine.

## Урок 8, блок D: фізичне видалення

`DELETE /api/transactions/{id}` без тіла, з `Authorization: Bearer <пароль>`.
Використовує той самий require_admin та middleware. Credentials перевіряються
до ID. ID: десятковий додатний BIGINT 1–9223372036854775807, без float.
Клієнтські user_id/headers не надають прав: власник тільки API_ALLOWED_USER_ID.

Одна транзакція виконує DELETE WHERE id=:id AND user_id=:owner RETURNING id.
Немає окремого SELECT власника. Категорії, користувачі й інші записи не змінюються.
204 повертається тільки після успішного виходу з transaction context (commit),
без JSON/тіла. Відсутній і чужий запис мають однаковий 404 Transaction not found.
Повторний DELETE дає 404; два конкурентні DELETE — один 204, другий 404.

401: credentials відсутні/неправильні; 403: локальний захист; 422: ID;
503: запис вимкнено або помилка транзакції. При транзакційній помилці:
`{"detail":"Deletion could not be confirmed; refresh before retrying."}`.
Ця відповідь не стверджує ні успішне видалення, ні гарантовану відсутність зміни.
SQL-помилка до commit виходить через session.begin(), який відкочує транзакцію.
Core DELETE виконується негайно, сесія нова, pending ORM objects відсутні;
явний flush не потрібний. Commit context може виконувати flush, але тут йому
нема що записувати. При commit error SQLAlchemy намагається відкотити активну
транзакцію; розрив з'єднання після server commit не дозволяє довести результат.
Немає автоматичного retry або грубого визначення результату лише за фазою.
Навіть помилка закриття сесії після commit не є доказом невиконання операції.

Frontend цього блоку не змінено. Майбутній клієнт має обробляти 204 без json(),
після успіху повторити GET списку й summary, а після мережевого збою спершу
перевірити стан. HTTP-ідемпотентність не означає однаковий статус повторів:
перший запит прибирає рядок, наступний уже нічого не змінює і повертає 404.

Видалення незворотне через dashboard і не створює журнал історії. Фізичне
видалення Telegram-операції прибирає також ключ дедуплікації повідомлення:
повторна обробка старого повідомлення потенційно створить витрату знову.
Бот і механізм дедуплікації цього блоку не змінені. Міграцій не потрібно.

Перевірки без міграційних наборів:

```powershell
.\.venv\Scripts\python.exe -B -m pytest tests/test_transaction_delete.py tests/test_transaction_delete_pg.py tests/test_transactions_api.py tests/test_transaction_post.py tests/test_expense_handler.py tests/test_expense_storage.py -p no:cacheprovider -q -rs
```

DELETE PostgreSQL-тести потребують наявного opt-in disposable local_engine
з conftest: окрема локальна expense_test, випадкова ізольована схема. Вони
не запускають SQL-міграції. Ін'єкція помилки перед commit перевіряє rollback,
але не моделює втрату підтвердження вже виконаного commit у мережі.

## Передумови та схема

API запускається окремо від Telegram. Імпорт не читає .env. DATABASE_URL,
API_ALLOWED_USER_ID та ADMIN_PASSWORD надходять із середовища; за потреби
наявний env-файл завантажує оператор через Uvicorn, а не модулі застосунку.
API_ALLOWED_USER_ID — перевірений внутрішній users.id, ніколи не Telegram ID.

Під час lifespan виконується read-only інспекція каталогу PostgreSQL: колонки,
NOT NULL, типи type/date/amount, defaults, CHECK, валідованість constraints,
унікальність категорії/Telegram-пари та зовнішні ключі операції.
Потрібна схема після 001 і 002. Застаріла/недоступна схема блокує запуск із
контрольованим повідомленням. Немає автоматичного DDL, міграцій або create_all.

Робоча Neon до 002 несумісна з новим API та вже оновленим ботом. Старий GET
міг працювати, оскільки не вибирав type/date. Спочатку окремо погодити й
застосувати 002, зберігши baseline двох старих витрат 120/75 та резервне
відновлення; потім перезапустити процеси, щоб не повторно використовувати
prepared statements зі старою схемою. Цей блок не застосовує SQL до Neon.

## Доступ

Зберігаються loopback, Host/Origin/Fetch Metadata, no-store, nosniff та вимкнений
CORS. Не публікувати через зовнішню адресу або тунель. GET не потребують пароля.

POST захищений спільною dependency require_admin, придатною для майбутнього
DELETE. ADMIN_PASSWORD читається тільки на startup, порівняння UTF-8 bytes —
secrets.compare_digest. Порожня/відсутня конфігурація вимикає запис (503),
але залишає GET. Заголовок запиту: Authorization: Bearer <введений пароль>.
Відсутній/некоректний пароль — 401 з WWW-Authenticate: Bearer. Перевірка
передує JSON parsing: навіть malformed JSON без credentials отримує 401.

Не передавати пароль у URL, тілі операції, VITE_*, Git або frontend bundle.
Не зберігати в localStorage; майбутній UI може тримати введений пароль у пам'яті.
Не експортувати HAR із credentials. Логи не містять headers, payload, SQL
або exception text. Це спільний локальний секрет без персональних ролей,
rate limiting і production-сесій. Для мережевого розгортання потрібні HTTPS
і повноцінна автентифікація. Локальні процеси й надалі можуть читати GET.

## Контракти

POST /api/transactions, Content-Type: application/json:

```json
{"type":"income","amount":"300.00","category":"Зарплата","description":"Виплата","date":"2026-11-21"}
```

Усі поля обов'язкові, невідомі заборонені. amount — тільки десятковий рядок
без експоненти, float, NaN/Infinity чи округлення: >0, <=9999999999.99,
максимум 2 знаки. category після trim: 1–100 символів; description: 1–2000.
NUL відхиляється. date — календарна YYYY-MM-DD; майбутні дати дозволені.
Категорії з різним регістром залишаються різними, семантика точних назв збережена.

Власник береться лише із сервера. Існуючий User перевіряється перед записом.
Одна транзакція створює/знаходить категорію через ON CONFLICT та вставляє
операцію; Telegram-поля NULL. Помилка відкочує й нову категорію. Лише після
commit повертається 201 із представленням операції:

```json
{"id":"17","created_at":"2026-11-21T10:00:00Z","date":"2026-11-21","type":"income","amount":"300.00","category":"Зарплата","description":"Виплата","currency":"UAH"}
```

GET /api/transactions повертає масив такого формату, справжній type та date.
Порядок created_at DESC, id DESC; limit 1–100 (default 50), offset >=0.
ID і гроші — рядки; DELETE описаний у блоці D вище.

Необов'язковий query-параметр `type`: `all` (за замовчуванням), `income`,
`expense`. Приклад: `GET /api/transactions?type=income&limit=20&offset=0`.
Невідоме або порожнє значення повертає 422 без відображення вводу.
SQL спочатку обмежує власника та тип, потім застосовує сортування й LIMIT/OFFSET.
Тіло відповіді залишається масивом; заголовок `X-Total-Count` містить кількість
усіх записів цього власника за вибраним фільтром до пагінації. Кількість і
сторінка читаються одним SQL statement; заголовок є також для порожньої
сторінки й offset за межами результатів. Старі клієнти можуть ігнорувати його.
React скидає сторінку на першу при зміні типу, показує відфільтровану кількість
і вимикає «Далі» на останній сторінці. Після створення/видалення фільтр
зберігається. Картки `/api/summary` продовжують охоплювати всі типи.

GET /api/summary одним SELECT агрегує всі операції власника, без пагінації:

```json
{"total_income":"300.00","total_expense":"195.00","balance":"105.00"}
```

Обчислення — NUMERIC/Decimal; відсутні суми дають 0.00. Balance — різниця,
не підтверджений банківський залишок. Список і summary — різні snapshots.

422: контрольовані помилки без echo вводу. 403: порушення локального доступу.
503: запис вимкнений або збереження не підтверджено/БД недоступна. Commit може
мати неоднозначний результат при втраті з'єднання: немає автоматичного retry.
Перед ручним повтором оновити список. HTTP idempotency ще не реалізована.

## React та наступний блок

React не змінено: картки приймають той самий summary JSON, але старі пояснення
ще говорять про відсутність доходів. API-клієнт таблиці приймає лише expense,
компонент завжди показує мінус. До frontend-блоку не створювати income в
робочому середовищі. Не маскувати доходи як витрати заради старого dashboard.

## Перевірки

```powershell
.\.venv\Scripts\python.exe -B -m pytest tests -p no:cacheprovider -q -rs
```

Реальні записи використовують тільки guarded local_engine: потрібні
EXPENSE_TEST_DB_DISPOSABLE=yes та окрема EXPENSE_TEST_DATABASE_URL на локальну
expense_test. Немає fallback на DATABASE_URL або читання .env. Без opt-in
PostgreSQL-тести пропускаються. SQLite GET-тести не доводять роботу PostgreSQL.
Dashboard integration піднімає лише ізольовані loopback HTTP/Vite та SQLite.
