# Безпека проєкту ai-saas-course

Цей документ описує базові правила захисту секретів навчального Telegram-бота та результати перевірок у межах уроку №4 — Logs, Errors & Debugging.

## Захист токена Telegram-бота

`BOT_TOKEN` дає доступ до керування ботом. Його потрібно зберігати як секрет: не додавати до коду, документації, повідомлень, скриншотів або логів.

- Для локального запуску токен задають через змінну середовища `BOT_TOKEN` або локальний файл `.env`.
- `.env` містить локальні налаштування та може містити секрети, тому його не додають до Git.
- `.env.example` — шаблон налаштувань для інших розробників. У ньому залишають назви змінних і безпечні приклади, без реальних значень секретів.

Безпечний приклад для `.env.example`:

```dotenv
BOT_TOKEN=
```

Після копіювання шаблону в локальний `.env` розробник самостійно заповнює токен. Повідомлення про відсутній токен може називати змінну `BOT_TOKEN`, але не повинно показувати її значення.

## Захист Git-репозиторію

`.gitignore` визначає файли, які Git має ігнорувати під час додавання нових файлів. Для цього проєкту важливо ігнорувати `.env` та інші локальні файли із секретами.

Ігнорування не припиняє відстеження файлу, який уже був доданий до Git, і не видаляє його з історії. Тому потрібно перевіряти і правила ігнорування, і список відстежуваних файлів.

Безпечні команди перевірки, які не показують вміст `.env`:

```powershell
git check-ignore -v -- .env
git ls-files -- .env
git log --all --oneline -- .env
```

Перша команда показує правило ігнорування. Відсутність виводу другої означає, що файл за цим шляхом не відстежується. Третя перевіряє коміти для вказаного шляху; вона не є повним пошуком секретів у всій історії.

Не додавайте до репозиторію токени, API-ключі, паролі, приватні ключі та конфіденційні експорти. Не використовуйте примусове додавання ігнорованих секретних файлів через `git add -f`.

## Перевірка секретів

`detect-secrets` шукає потенційні секрети у файлах. Його результати потребують перевірки людиною: відсутність знахідок не гарантує, що секретів немає.

За результатами вже проведених перевірок:

| Перевірка | Результат |
| --- | --- |
| Ігнорування `.env` | `.env` ігнорується Git. |
| Відстеження `.env` | `.env` не відстежується Git. |
| `git log --all --oneline -- .env` | Комітів із файлом за вказаним шляхом не показано. |
| Сканування поточних відстежуваних файлів через `detect-secrets` | Потенційних секретів не виявлено. |
| Окреме сканування `.env.example` | Потенційних секретів не виявлено. |
| Повна перевірка історії Git | Не завершена через помилки розпакування архівів. |

Отже, результати стосуються перевірених файлів та зазначеного шляху. Стверджувати, що вся історія Git не містить секретів, підстав немає.

Приклад повторного сканування шаблону за наявності встановленого `detect-secrets`:

```powershell
detect-secrets scan .env.example
```

Не публікуйте необроблені звіти сканування без перегляду: вони можуть містити конфіденційні назви файлів або інші службові дані. Не копіюйте реальні секрети в опис знайденої проблеми.

## Дії у випадку витоку токена

Якщо токен потрапив у Git, публічне повідомлення або інше ненадійне місце, вважайте його скомпрометованим.

1. Відкличте поточний токен через офіційного Telegram-бота BotFather, вибравши відповідного бота.
2. Отримайте новий токен через BotFather. Не публікуйте його.
3. Оновіть `BOT_TOKEN` у локальному `.env` або в захищених налаштуваннях середовища запуску.
4. Перезапустіть бота, щоб він почав використовувати новий токен. Перевірте запуск без виведення значення токена.
5. Усуньте джерело витоку: приберіть секрет із поточних файлів, перевірте логи та доступні копії. Якщо секрет потрапив у Git, окремо сплануйте очищення історії та узгодьте його з учасниками проєкту.

Просте видалення токена з останньої версії файлу не прибирає його з попередніх комітів і не замінює відкликання.

## Правила безпеки перед комітом

Перевірте список змінених файлів і поточні зміни:

```powershell
git status --short
git diff --name-only
git diff
```

Додавайте до майбутнього коміту лише потрібні файли за явними шляхами. Потім перевірте саме підготовлені зміни:

```powershell
git diff --cached --name-only
git diff --cached
git diff --cached --check
```

Команди `git diff` можуть показати секрет, якщо його випадково записали у відстежуваний файл. Переглядайте результат локально та не пересилайте його без перевірки. `git diff --cached --check` перевіряє проблеми форматування, а не наявність секретів.

Перед створенням коміту переконайтеся, що:

- серед підготовлених файлів немає `.env` або інших конфіденційних файлів;
- у коді, документації, прикладах і логах немає реальних секретів;
- `.env.example` містить лише безпечний шаблон;
- доступне сканування секретів виконане, а знайдені попередження розглянуті;
- до коміту потрапляють лише заплановані зміни.

Якщо секрет випадково підготовлено до коміту, зупиніть підготовку та усуньте проблему до створення коміту. Якщо секрет уже оприлюднено, виконайте процедуру відкликання та заміни.
