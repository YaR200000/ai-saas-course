## Урок 3. Telegram-бот на Python та Docker

### Призначення та можливості

Навчальний Telegram-бот демонструє асинхронні обробники команд на Python з aiogram 3.x. Бот отримує повідомлення через polling і підтримує дві команди:

- `/start` — надсилає привітання.
- `/help` — показує список доступних команд українською.

### Структура файлів

```text
ai-saas-course/
├── app/
│   ├── __init__.py     # Python-пакет застосунку
│   └── main.py         # Обробники команд і запуск polling
├── requirements.txt   # aiogram, python-dotenv, watchfiles
├── Dockerfile         # Образ Python 3.12 slim і встановлення залежностей
├── compose.yaml       # Сервіс bot, змінні середовища та режим розробки
├── .dockerignore      # Виключення секретів і зайвих файлів зі збірки
├── .gitignore         # Виключення локальних файлів із Git
├── .env.example       # Шаблон змінних без справжнього токена
├── .env               # Локальний файл із токеном, створюється вручну
└── README.md          # Документація проєкту
```

### Вимоги для запуску

- Для локального запуску: Python 3.12 з pip і Windows PowerShell.
- Для запуску в контейнері: встановлений і запущений Docker Desktop з Docker Compose (`docker compose`) та підтримкою Linux-контейнерів. Локальний Python для цього способу не потрібний.
- Інтернет-з'єднання та Telegram-бот із токеном, отриманим у BotFather.

Усі команди нижче виконуйте з кореня репозиторію `ai-saas-course`.

### Налаштування BOT_TOKEN

Якщо `.env` ще не існує, створіть його з шаблону в PowerShell:

```powershell
Copy-Item .env.example .env
```

Не перезаписуйте вже налаштований `.env`. Відкрийте його локально в редакторі й замініть значення-заглушку `BOT_TOKEN` на власний токен із BotFather. Не публікуйте токен, не вставляйте його в навчальні промпти, скриншоти чи команди термінала.

`.gitignore` виключає `.env` із Git, а `.dockerignore` виключає `.env` і `.env.*` із контексту збірки. Dockerfile не містить токена. Compose передає змінні з `.env` у контейнер під час запуску через `env_file: .env`.

Під час локального запуску `python-dotenv` читає `.env` із кореня проєкту. Якщо `BOT_TOKEN` уже заданий у змінних середовища, він має пріоритет. Без непорожнього токена бот завершує запуск із повідомленням про помилку.

### Локальний запуск у Windows PowerShell

Створіть і активуйте віртуальне середовище, встановіть залежності та запустіть бота:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m app.main
```

Якщо PowerShell блокує скрипт активації, можна запускати Python середовища напряму, без активації:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m app.main
```

Зупиніть локальний процес натисканням `Ctrl+C`. Звичайний локальний запуск не вмикає автоматичний перезапуск. Детальніше про середовища — у [документації Python venv](https://docs.python.org/3/library/venv.html).

### Запуск через Docker Compose

Після налаштування `.env` і запуску Docker Desktop виконайте:

```powershell
docker compose up --build
```

Compose збирає образ із залежностями та запускає сервіс `bot`, показуючи його вивід у терміналі. Локальне віртуальне середовище для цього не використовується. Команда сервісу запускає `python -m app.main` через `watchfiles`; політика `restart: unless-stopped` збережена. Параметр `--build` описаний у [документації Docker Compose](https://docs.docker.com/reference/cli/docker/compose/up/).

Не запускайте одночасно локальну й Docker-версії з одним токеном: обидві намагатимуться отримувати оновлення одного бота через polling. Перед переходом у Docker зупиніть локальний процес через `Ctrl+C`; перед локальним запуском зупиніть контейнер.

### Автоматичний перезапуск під час розробки

У `compose.yaml` каталог `./app` монтується в `/app/app` через bind mount. Збережені локально зміни стають доступними всередині контейнера без повторної збірки образу.

Сервіс виконує команду:

```text
watchfiles --filter python "python -m app.main" /app/app
```

`watchfiles` запускає бота, рекурсивно стежить за Python-файлами каталогу `app` і після змін зупиняє та повторно запускає Python-процес. Сам контейнер при цьому не перебудовується. `WATCHFILES_FORCE_POLLING: "true"` вмикає періодичну перевірку файлів для роботи зі змонтованим каталогом, зокрема на Windows. Це окремий механізм від політики перезапуску контейнера `unless-stopped`.

Після зміни `requirements.txt` або Dockerfile знову виконайте `docker compose up --build`, щоб оновити образ. Деталі роботи спостерігача: [CLI watchfiles](https://watchfiles.helpmanual.io/cli/) та [режим polling](https://watchfiles.helpmanual.io/api/watch/#force-polling).

### Зупинка контейнера

В іншому вікні PowerShell, відкритому в корені проєкту, виконайте:

```powershell
docker compose stop
```

Команда зупиняє контейнер без його видалення. Після явної зупинки політика `unless-stopped` не запускає його знову автоматично. Дивіться [документацію docker compose stop](https://docs.docker.com/reference/cli/docker/compose/stop/).

### Перевірка в Telegram

Запустіть один екземпляр бота й відкрийте в Telegram чат із ботом, для якого налаштували токен.

1. Надішліть `/start`. Очікувана відповідь: «Привіт! Я працюю через Docker з автоматичним оновленням! 🐳🚀». Цей текст однаковий і за локального запуску.
2. Надішліть `/help`. Очікувана відповідь:

   ```text
   🤖 Доступні команди:
   /start — привітання
   /help — список доступних команд
   ```

Для перевірки автоматичного перезапуску під час роботи через Compose змініть текст відповіді в `app/main.py`, збережіть файл, дочекайтеся перезапуску процесу та повторно надішліть відповідну команду в Telegram.

## Урок 4. Логи, помилки та налагодження

### Мета уроку

Навчитися записувати події роботи програми в логи, діагностувати помилки за повідомленнями та traceback і документувати причини, виправлення та результати перевірок.

### Логування в app/main.py

Використовується стандартний модуль Python `logging`. Logger створено через `logging.getLogger(__name__)`, а в `main()` налаштовано `logging.basicConfig` з рівнем `logging.INFO` та форматом:

```text
%(asctime)s | %(levelname)s | %(message)s
```

Кожен запис містить час, рівень і повідомлення. Рівень INFO дозволяє бачити інформаційні повідомлення та серйозніші події, зокрема ERROR; повідомлення DEBUG за такого налаштування не показуються.

| Подія | Рівень | Повідомлення |
| --- | --- | --- |
| Перед початком polling | INFO | `bot started` |
| Обробка `/start` | INFO | `received /start command` |
| Обробка `/help` | INFO | `received /help command` |
| Відсутній або порожній `BOT_TOKEN` | ERROR | `BOT_TOKEN не задано або порожній. Запуск бота припинено.` |

INFO описує звичайний перебіг роботи, ERROR повідомляє про помилку. Перед створенням бота значення `BOT_TOKEN` очищається від пробілів на початку та в кінці. Якщо воно порожнє, програма записує ERROR і завершує запуск через `SystemExit` зі зрозумілим поясненням. У цьому випадку traceback відсутній. Значення токена в ці повідомлення не потрапляє; відповіді `/start` та `/help` збережено.

Ця перевірка стосується наявності токена. У коді немає окремого універсального обробника всіх винятків або спеціальної обробки мережевих помилок.

### Перегляд логів

Під час локального запуску логи видно в тому самому терміналі:

```powershell
.\.venv\Scripts\python.exe -m app.main
```

Окремий файл логів у коді не налаштовано. Стандартний обробник `logging` виводить повідомлення в потік помилок термінала (stderr).

Під час запуску через `docker compose up --build` вивід сервісу видно в терміналі Compose. Для перегляду останніх повідомлень і подальшого спостереження за сервісом `bot` в іншому терміналі використовуйте:

```powershell
docker compose logs --tail 100 -f bot
```

Compose може додавати до рядків префікс сервісу. Не запускайте локальний бот і контейнер одночасно з одним токеном. Наведені команди — інструкції для перегляду логів, а не звіт про додаткове тестування Docker в уроці №4.

### Досліджені помилки

У [DEBUG.md](DEBUG.md) зафіксовано два випадки:

1. **Missing BOT_TOKEN.** Для тесту рядок токена в локальному `.env` тимчасово закоментували, а змінна в PowerShell була відсутня. Програма записала ERROR та завершилася через `SystemExit`. Після відновлення рядка повторний запуск показав `bot started`, `Start polling` і `Run polling for bot ...`: бот розпочав polling. Під час завершення тесту виникли `CancelledError`, `KeyboardInterrupt` і повідомлення про мережеве відключення. Це окремі події завершення роботи; точну причину мережевого відключення не встановлено.
2. **ModuleNotFoundError.** Окремою командою `python -c` навмисно спробували імпортувати вигаданий `nonexistent_training_module`. Traceback указав на перший рядок переданого коду та завершився повідомленням `ModuleNotFoundError: No module named 'nonexistent_training_module'`. Для перевірки неправильний імпорт замінили на імпорт стандартного `logging` й отримали `Import successful: logging`. Вигаданий модуль не встановлювали, код Telegram-бота для цього тесту не змінювали.

### Документація налагодження та безпеки

- [DEBUG.md](DEBUG.md) — журнал досліджених помилок: команди відтворення, фактичні повідомлення, гіпотези, причини, способи виправлення та перевірки. Запити до AI в ньому чітко позначено як приклади.
- [SECURITY.md](SECURITY.md) — правила зберігання секретів, результати перевірок, дії після витоку токена та перевірка змін перед комітом.

### Захист BOT_TOKEN і перевірка секретів

Токен зберігають у локальному `.env` або змінній середовища `BOT_TOKEN`. `.env.example` слугує шаблоном без реальних секретів. Токен не додають у код, документацію, логи чи промпти до AI. `.gitignore` захищає від випадкового додавання нових конфіденційних файлів, але не видаляє вже відстежувані файли або попередні коміти.

За проведеними перевірками, задокументованими в `SECURITY.md`:

- `.env` ігнорується Git і не відстежується ним;
- `git log --all --oneline -- .env` не показала комітів із файлом за цим шляхом;
- `detect-secrets` не виявив потенційних секретів у поточних відстежуваних файлах та під час окремої перевірки `.env.example`;
- повне сканування історії Git не завершене через помилки розпакування архівів.

Ці результати не підтверджують відсутність секретів у всій історії репозиторію. Перед комітом потрібно переглядати список файлів і підготовлені зміни через `git status --short`, `git diff --cached --name-only` та `git diff --cached`, не публікуючи секретні дані. У разі витоку токен відкликають через BotFather, отримують новий, оновлюють налаштування та перезапускають бота.

### Підсумки уроку

Додано базове логування запуску та команд бота, досліджено відсутність токена й помилку імпорту, оформлено документи з налагодження та безпеки. Відпрацьовані навички: читання логів INFO та ERROR, пошук головного рядка traceback, перевірка гіпотез окремими командами, розрізнення фактичних результатів і припущень та безпечна робота із секретами.
